四个 AI Agent 被放进一个随机生成的《Minecraft》生存世界。它们收到的核心目标只有一个：击败末影龙。研究人员没有为它们安排角色，也没有编写“怎样通关”的专用路线；真正负责推进任务的是四个通用 Coding Agent。

最终它们花了 **27 小时 14 分钟**，运行 **2,783 段自己编写的程序**，在经历 **605 次死亡** 后完成目标。这个数字听起来像游戏趣闻，但更值得追问的是：一个由大量相互依赖步骤组成的任务，为什么可以连续运行一天以上而没有彻底失去方向？

这篇研究提供的不是“Agent 玩游戏很厉害”的泛泛结论，而是一份少见的长程执行记录。它让我们有机会具体观察：Agent 怎样发现自己需要合作、如何把失败变成记忆、怎样建立工具、又如何确认最终目标真的完成。

## 游戏界面被换成了“编程接口”

首先需要澄清：四个 Agent **并不是像人一样看着 Minecraft 画面，用键盘和鼠标操作**。

研究团队使用了开源 JavaScript 机器人库 **Mineflayer** 及其寻路插件。每个 Agent 在独立的计算环境里编写简短的 JavaScript 程序，再通过 Mineflayer 控制自己的游戏角色。程序可以读取位置、生命值、背包、周围方块和生物，也可以下达移动、挖掘、合成、攻击等操作。

执行后，Agent 收到的是文本化结果或错误，再据此决定下一步。一个基本循环可以概括为：

```text
观察游戏状态
    ↓
规划下一项动作
    ↓
编写 JavaScript
    ↓
通过 Mineflayer 执行
    ↓
读取日志、错误与世界变化
    ↓
更新计划和记忆
```

因此，这个实验测试的核心并非视觉理解能力，而是**通用 Coding Agent 能否在一个长期、可操作、持续变化的环境中解决问题**。这一区别很重要，因为 Mineflayer 能暴露一些玩家仅靠视觉难以直接获知的结构化信息，降低了感知与导航的难度。

## 从无到有：27 小时里的三个关键转折

第一阶段是团队自行形成分工。游戏开始约十分钟，某个 Agent 就在聊天中提出协作安排。随后团队逐渐形成了寻找食物、采矿与制作工具、修建传送门等不同职责。没有集中式指挥者事先列出“你负责 A，我负责 B”的剧本，分工是在同一个目标和共享环境中逐步产生的。

第二阶段体现了“从观察到策略”的能力。为了寻找末地要塞，Agent 从两个位置投掷末影之眼、采集飞行轨迹，再用两条方向线的交点估算要塞位置。论文记载，这个估计距离实际传送门房间约 **43 米**，而目标距离出发村庄约 **1.3 公里**。

更有意思的是运输和恢复过程：携带关键物资的队友在途中死亡后，其余 Agent 分享死亡位置和物品消失前的时限，最终及时取回物资。这类行为很像真实软件任务中的事故恢复：重要的不是“绝不出错”，而是**错误发生后，团队能否保留足够状态并正确接续**。

第三阶段最能暴露长程执行的困难。四个 Agent 抵达末地后，并没有立刻结束任务；末影龙战斗持续了近十四小时，团队在最终阶段死亡了数十次。经过反复失败，Agent 找出了龙不断回血与高塔上的治疗水晶有关，继而采用堆叠泥土爬高的方式逐个摧毁水晶。

这里值得关注的不是某个单独的“聪明动作”，而是一个完整的闭环：**识别异常 → 提出原因 → 尝试新策略 → 从环境得到反馈 → 修订行动方案**。

## 为什么多 Agent 没有变成四个彼此干扰的脚本？

研究中出现了几种对 Agent 工程特别有参考价值的行为。

**第一，角色专业化（Specialization）。** 团队成员根据任务需求自然分配工作。这并不意味着每个 Agent 都拥有不同模型或专用技能；它们使用相同的通用 Coding Agent，而分工来自协作过程。

**第二，共享记忆（Shared Memory）。** 队伍会记录箱子、传送门、危险区域的坐标，以及工具和游戏机制中的坑。例如，某个 Agent 早期发现一个 Mineflayer 合成行为的注意事项；这个修正后来被其他成员重复采用。一次发现成为团队资产，而不是停留在某个会话的短期上下文里。

**第三，自制工具（Self-authored Helpers）。** Agents 不只反复调用基础 API，也会逐渐封装自己需要的辅助功能。论文记录了 **42 个辅助函数**，涉及维持漂浮、计数、限时行走、控制已超时程序的残留动作等。可复用的局部工具降低了后续重复工作量。

**第四，纠错与互相校验。** 一段程序可能错误地报告某个目标已经达成；研究记录里，Agent 会撤回虚假的成功报告，队友也会指出与已知事件冲突的说法。这个例子说明：**执行日志中的“成功消息”不应被直接等同于环境中的真实成功**。

这些行为并不证明多 Agent 一定优于单 Agent——论文没有为此设计对照试验。但它确实展示了一个长期任务中，协作能够以何种具体形式出现。

## 第五个 Agent 不参加游戏，只负责作证

除四名玩家外，研究人员还放置了一个独立的 **Observer（观察者 Agent）**。

Observer 不执行游戏操作。它阅读过程记录、检查玩家报告是否与证据一致，并观察是否出现钻规则漏洞、捏造结果等行为。研究人员也可以通过实时面板查看运行情况并暂停实验。

这种设置背后有一个重要工程原则：**负责执行任务的系统，不应该成为唯一负责证明任务成功的系统。**

最终胜利由游戏服务器日志中的成就事件确认，而不只是由某位玩家在聊天里宣布“赢了”。研究还保留了程序、输出、对话和服务器事件，以便事后审计。

这里的 Observer 不是绝对可靠的形式化验证器，但它与客观游戏日志组合起来，构成了比 Agent 自我汇报更强的证据链。

## 不能忽视的另一面：错误、成本与实验边界

这是一项令人印象深刻的演示，但距离“生产级可靠性”仍有明显差距。

论文明确指出，实验只展示了**一次运行**，不足以给出成功率分布；难度设置为 Easy，模型也已从训练数据中掌握大量 Minecraft 知识。Mineflayer 提供结构化感知和寻路能力，不能与视觉、鼠标和键盘操作直接比较。全程约 **22% 的程序以错误结束**，服务器还经历了六次重启。

成本也值得认真看待。直到击败末影龙，四名玩家合计处理了约 **13.5 亿输入 Token**，其中约 **91% 命中上下文缓存**，并产生约 **1,600 万输出 Token**。按照论文所采用的发布初期 API 列表价格，估算约 **520 美元**；按更高的标准价格估算约 **1,040 美元**。这不是 Google 实际推理成本，也不代表类似任务普遍都能以这一价格完成。

因此，这项研究最稳妥的结论是：**一个配备代码执行接口、持久记忆和协作机制的 Agent 团队，在特定环境中的一次长程任务里表现出了持续推进与恢复能力。** 它尚不能证明相同机制能够稳定解决任意现实世界项目。

## 译者观察：真正值得复用的是“可恢复的执行系统”

以下内容是我对独立开发和 Agent Harness 的延伸分析，不是论文作者的直接结论。

### 1. 把长程任务设计成有状态的执行过程

很多 Agent Demo 只有一条对话链：用户输入目标，模型调用工具，然后返回答案。一旦会话过长、上下文压缩或工具失败，系统就容易忘记之前做到哪里。

Minecraft 实验提示我们，更实用的抽象可能是：

```text
Objective
  ├─ Verified world state
  ├─ Pending tasks / dependencies
  ├─ Shared decisions and lessons
  ├─ Reusable actions / helpers
  ├─ Failure log and recovery checkpoints
  └─ Evidence of completion
```

对 Coding Agent 而言，上述字段分别可以映射到目标验收条件、Git 状态与测试结果、任务依赖图、共享 ADR、可重复运行的脚本、重试记录与最终验收证据。

### 2. “记住失败原因”比“记住整个过程”更有价值

一个 Agent 不需要无限保留所有对话。它需要能把重复出错的地方提炼成可检索、可执行的约束。

例如，将“部署失败了三次”压缩成“生产环境禁止使用某种配置；正确操作步骤是……”，并为这条经验附上具体日志与适用范围。这样记忆才从聊天摘要升级为工程资产。

### 3. 让验证者与执行者分离

可以为长程 Agent 工作流增设一个低权限 Reviewer / Observer。它只读取 PR Diff、测试日志、运行状态与目标定义，并独立判断：

- 关键验收条件是否有证据；
- “完成”的说法是否和实际状态一致；
- 是否在重试中意外扩大了操作范围；
- 哪些结果仍需要人工确认。

要注意：只读 Observer 不能替代单元测试、权限边界和端到端验证，但可以减少“Agent 自己说成功就算成功”的结构性风险。

### 4. 可以马上做的三个小实验

**实验 A：跨会话接力。** 选一个需要 30–60 个步骤的开发任务，故意在中途清空上下文。比较有无持久状态文件时，Agent 恢复任务所需的时间、重复调用量和最终成功率。

**实验 B：共享经验复用。** 让两个 Agent 处理相似仓库问题，允许第二个读取第一个经过验证的失败复盘。记录它是否更少重复错误，同时防止把不适用的经验错误迁移过来。

**实验 C：独立验收。** 同一任务分别测试“执行者自报完成”和“只读 Observer + 客观测试确认”两种方式，比较误报成功、漏报失败和额外 Token 成本。

最终值得追求的，不是让 Agent 更久地连续输出，而是让它在长时间内仍然能够**保持目标、保存证据、从错误中恢复，并在不确定时诚实地报告状态**。

这或许才是从 Coding Agent 演示走向可靠 Agent 系统最关键的一步。
