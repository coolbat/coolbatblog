AI 已经能帮助我们生成代码、寻找数学表达式、拟合观测数据，甚至自动提出并运行一套模型。但科学研究最终想得到的不是一份“结果看起来正确”的文件，而是一个更困难的东西：**为什么这个解释成立，其他解释又为什么不成立？**

三位来自图宾根的研究者在新文章中提出一个值得重视的区分：计算可以越来越自动化，但科学洞察不能简化成寻找预测误差最低的答案。让 AI 参与科学研究，需要同时重新设计模型的**构建、约束与解释**三个环节。

## 一、一个四次方，为什么能解释神经细胞？

1951 年，研究神经冲动的 Alan Hodgkin 与 Andrew Huxley 面对一个艰难问题：怎样用方程描述神经细胞电信号的产生？当时剑桥大学的计算机停机数月，Huxley 不得不花数周用机械计算器处理方程。

他们发现，为了让理论曲线符合实验测量，描述某类离子通道开放过程的变量需要出现四次方。它首先是从数据中得到的经验形式，但研究者没有就此停止。他们进一步思考：这是否暗示通道开放需要多个独立的微观事件共同发生？

几十年后，相关钾离子通道的结构研究发现了四个相同亚基围绕中央通道排列的构造。原文用这个例子说明：一个数学形式的价值，超出了“拟合成功”；它还可能指向尚未直接看见的物理机制。

但要特别谨慎：后来发现的相关通道结构，并不意味着当年方程中的每个微观细节都被直接证明。科学理解依赖证据链，而非事后把模型和发现简单画上等号。

## 二、三个环节：构建、约束、解释

**构建模型（Building）**：决定模型包含哪些变量、结构与关系。比如研究者应选择何种微分方程，哪些机制不可省略。

**约束模型（Constraining）**：利用实际测量来限制参数的可能范围。参数拟合不只是求出一组最佳数字，更是要知道哪些参数被数据可靠限定，哪些仍有多种可能。

**解释模型（Interpreting）**：从模型中提炼关于真实世界的可检验主张，包括它在新条件下会作何预测，以及为什么一些替代解释不能成立。

这三个环节会反复循环。模型可能拟合得很好，却无法支持人们原本期待的机制解释；此时不应只继续调参，而需要返回构建阶段重新提出假设。

## 三、从“最佳参数”转向“不确定性的地图”

在复杂系统里，很多不同的参数组合都能生成近似的观测结果。若只报告一组看似最优的参数，我们很容易误以为已经知道了系统内部发生了什么。

文章重点介绍了**基于模拟的推断（Simulation-Based Inference，SBI）**。思路是：从大量参数候选出发，多次运行模拟器，记录“参数 → 输出”的关系，再训练神经网络根据新的观测数据反推可能的参数分布。

这种方法对无法方便写出似然函数、但能运行正向模拟的模型尤其有用。它不保证我们找到了真相，但能提供一幅比单一答案更诚实的地图：哪些区域被观测支持，哪些存在多种解释，以及下一次实验最应该消除什么不确定性。

原作者举到神经元、宇宙学等场景，并指出模拟通常仍很昂贵；训练完成后的网络则可能大幅加速对新数据的推断。

## 四、AI 参与“发明模型”，也必须保留失败的候选

今天，基于 LLM 的 Agent 已经能够编写候选模型代码、运行模拟、比较实验数据，再自动修改模型结构。这把 AI 从辅助拟合参数推进到了辅助提出科学假设。

但这里存在一个容易忽视的陷阱：**同一组数据可能允许多个不同模型同时成立。**

一个 Agent 如果只给出“排名第一”的方程，就隐藏了科学家最需要知道的信息：是否还有其他机制同样解释观测？哪些性质是所有可行模型共同拥有的？模型因为增加自由度才拟合得好，还是因为确实抓住了数据中的规律？

作者因此主张，不仅要考察参数的分布，还要考察**模型本身的候选分布**。比较模型的适配度、复杂度与共同特征，才能发现稳健结论，也才能找出值得设计新实验的分歧点。

研究者同时强调了现阶段的边界：相关 AI 系统主要在重新发现已有科学知识的任务上接受检验，对未知答案的真正新问题，可靠证据仍然有限。

## 五、解释不是给结果再补一段漂亮文字

一个模型预测得准，不等于人们理解了它。有时真正关键的不是它在已观察条件下输出什么，而是**主动干预系统时，不同模型是否给出一致预测**。

例如，如果多个符合历史数据的神经元模型，在某种离子通道受到阻断的情况下预测一致，研究者就有了更稳健的判断；如果它们显著分歧，下一步实验就应优先调查这个分歧。

因此，AI 科研系统不应只交付答案。更好的交付物还包括：替代解释、证据支持的边界、失效案例、可辨识的机制以及下一轮实验建议。

这与单纯让 LLM 输出一篇“原因分析”不同。后者可能很流畅，前者则必须接受现实数据和反例的检验。

## 译者观察：Agent 应该交付“判断依据”，而不只是结果

上面是原作者围绕科学建模提出的核心论证。以下是我从独立开发与 Agent Harness 角度做的延伸。

对软件 Agent 来说，科学模型的三步过程可以转写成一个工程循环：

`提出候选方案 → 用外部证据验证 → 解释为什么选择它 → 保留反例与未知项`

今天很多 Coding Agent 已经擅长给出一个可运行的解决方案，但“跑通”不意味着设计已经合理。一个前端实现能够正常显示，可能仍然牺牲了可访问性；一个检索策略在三份文档上有效，可能在数据规模扩大后迅速失效。

如果 Agent 只提交最终代码，使用者将很难区分：它真的探索并排除了替代方案，还是碰巧找到了一个通过当前测试的实现。这种盲区也会加深项目的理解债务。

### 可以直接做的三个工程实验

**实验 A：单答案与多候选对比。** 对同一批真实 Issue，让 Agent 分别按“直接给最佳实现”和“先给两个可检验方案”运行。比较最终任务成功率、总 Token 消耗、后续需求变更时的修复成本。不要预设多候选一定更好。

**实验 B：保留被否决的证据。** 在 DeepSeek Harness 中增加精简的 Decision Record，记录候选、验证方式、失败原因及残余风险。重点衡量这些记录能否减少下一次相似任务中的重复错误，而不是记录越长越好。

**实验 C：用主动扰动代替只测标准样例。** 给 Agent 交付的系统施加参数变化、异常输入、网络抖动或数据分布变化，观察不同实现的行为。若两个方案在正常样例上打平，异常条件下的分歧通常更能指导下一轮设计。

这也可以迁移到 Agent Readiness Checker：与其只输出一个总分，不如同时给出测试路径、证据截图、失败案例、对照策略及可复测的验收条件。用户真正需要的不是“83 分”，而是知道**什么能被可靠验证，什么依旧是推断**。

文章让我再次想到一个经常被 AI 生成效率遮蔽的问题：**把寻找答案的成本降到极低之后，解释答案的责任并没有消失。** 对科学如此，对生产级 Agent 系统亦然。
