AI Coding Agent 已经越来越会写代码，但它们的商业模式仍然大多停留在旧的软件时代：按席位、按调用量、按 Token 或算力收费。

这会产生一个很直接的问题：**用户支付的是“Agent 做了多少工作”，而不是“Agent 最终交付了多少价值”。**

Sourcegraph 最近为 Agentic Batch Changes 选择了一条不同的路径：只有 Agent 生成的 changeset 最终被合并进代码库，客户才付费；没有合并，就不收费。

这篇文章真正值得关注的并不是 Sourcegraph 的具体价格，而是背后的产品判断：当 Agent 能够替人执行完整工作流时，SaaS 的计费单位可能需要从“使用软件”迁移到“完成工作”。

## Token 很容易计量，却很难代表价值

今天的大多数 Coding Agent 都按使用量收费。模型读了多少上下文、输出了多少 Token、运行了多少分钟，最终都能转化成账单。

这种方式对供应商很自然，因为计算成本本身就是按使用量发生的。

但对购买者而言，它留下了一个越来越明显的错位：一个 Agent 可以消耗大量 Token、提交很多 Pull Request，却不一定真正把事情做完。

对工程负责人来说，真正需要回答的问题通常不是：

**“这次迁移消耗了多少百万 Token？”**

而是：

**“这项迁移到底完成了吗？”**

这也是 Sourcegraph 文章的出发点。代码生成本身正在迅速变便宜，真正昂贵的是把变化推进到生产环境：跨仓库协调、等待 Review、处理冲突、修复测试、跟踪遗漏，最后确认迁移已经真正结束。

因此，单纯生成一个 diff 还不能算作最终结果。

Sourcegraph 选择把“已合并的 changeset”作为收费单位，本质上是把商业指标直接绑定到了客户可以验证的工程结果上。

## 为什么通用 Agent 很难采用结果计费

文章提出了一个很重要的产品边界：**并不是所有 Agent 都适合 outcome-based pricing。**

通用 Agent 可以被拿去写代码、查资料、做旅行计划、整理文件，任务开放度极高。对于这种产品，供应商很难定义一个稳定、客观、可计量的“成功结果”。

而 Agentic Batch Changes 是一个非常窄的专用 Agent。它面对的是一个清楚的问题：在大规模代码库中执行批量修改和迁移，并把修改推进到可合并状态。

因此它可以明确回答：

- 任务边界是什么；
- 什么状态算完成；
- 哪个结果可以被机器验证；
- 哪个事件可以作为计费触发点。

这带来一个很有意思的关系：

**Agent 越专用，结果往往越容易定义；结果越容易定义，越有可能按结果收费。**

这也说明，Agent 产品的商业模式其实和 Harness 设计紧密相关。

Sourcegraph 特别强调，他们不是简单地为每个仓库启动一个昂贵的通用 Coding Agent。如果一个普通脚本就能完成批量工作，系统会优先使用脚本；只有需要推理和适应性的地方才调用 Agent。

这不是单纯的工程优化，而是商业模式成立的前提。

如果供应商承诺“只有成功才收费”，那么失败尝试、无效推理、重复 Tool Call 和不必要的模型使用，都会直接变成供应商自己的成本。

于是，**成本效率从客户的问题变成了产品自己的问题。**

## 按结果收费，本质上是在重新分配风险

传统 Token 计费的风险主要由客户承担。

无论模型最后有没有解决问题，推理已经发生，账单也已经产生。

结果计费则把一部分风险转移给供应商：只有当系统真正完成目标时，供应商才能获得收入。

这会迫使产品团队关心一些在普通 API 生意里很容易被忽略的指标：

- 完成率，而不只是调用量；
- 单个成功结果的平均推理成本；
- 从首次执行到最终完成所需的重试次数；
- Review 和人工介入的比例；
- 哪些任务应该交给确定性脚本，哪些任务才值得调用 LLM。

也就是说，一旦选择 outcome-based pricing，Agent 产品就会自然地开始优化 **unit economics of success**——“一个成功结果到底需要花多少钱”。

这比单纯优化每百万 Token 的价格更接近真正的产品经济学。

## 一个真实案例：大规模迁移的价值不在 PR 数量

Sourcegraph 在文章中提到，Canva 团队在 Beta 阶段用 Agentic Batch Changes 执行一次库迁移，最终在多个仓库中合并了 50 多个 Pull Request。

这个案例的重要之处不是“Agent 自动开了很多 PR”。今天生成几十个 PR 已经并不稀奇。

真正的产品价值在于：这些变化被统一追踪、Review，并最终真正进入代码库。

因此，Sourcegraph 的账单也是围绕最终成功合并的 changeset 计算，而不是围绕 Agent 曾经打开过多少 PR，或者在过程中消耗了多少计算资源。

它把“做了很多事”和“完成了一件事”区分开了。

## 译者观察：这对独立开发者意味着什么

对独立开发者来说，这篇短文最值得借鉴的其实不是“以后所有 AI 产品都应该按结果收费”。

更重要的问题是：**你的产品有没有一个足够清晰、足够可验证的价值单位？**

很多 AI 产品今天仍然按照非常容易实现的计费方式设计商业模式：

- 每月多少次生成；
- 每月多少 Credits；
- 每月多少 Token；
- Pro / Ultra / Max 不同额度。

这些是成本单位，却不一定是客户真正愿意购买的价值单位。

如果一个 Agent 产品能够找到稳定的 outcome，就可能出现完全不同的定价方式。

例如：

- SEO Agent：按成功发布并通过检查的页面收费；
- Agent Readiness 工具：按修复并重新验证通过的问题收费；
- 文档转换 Agent：按成功转换且通过结构校验的文档收费；
- Coding Agent：按合并的 Pull Request 或关闭的工程任务收费；
- 数据采集 Agent：按通过质量检查的有效记录收费。

这里真正困难的不是支付系统，而是 **Verification**。

如果无法可靠判断任务是否成功，就无法安全地按成功收费。

因此，结果计费最终会把产品设计拉回到 Agent 工程里最核心的几个问题：

**什么叫完成？谁来验证完成？失败是否可恢复？质量阈值如何定义？**

这也是这篇文章最值得记住的一点：

**Agent 产品的定价模型，不只是商业部门最后加上的一层，它可以反过来决定 Harness、Eval、权限、工具选择和整个系统架构。**

当一个产品敢于只为成功结果收费时，它实际上是在用商业模式告诉用户：我们愿意为 Agent 的失败承担成本。

对于下一代垂直 Agent，这可能会成为一个非常重要的竞争维度。
